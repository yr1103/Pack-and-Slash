# Comment Convention

> 코드에 주석을 작성·수정 매뉴얼을 정리한 컨벤션 문서이다. 승인된 코드 작업에서 **의도·계약·예외 이유**를 정확히 남기도록 한다.


## 1. 주석 작성 원칙

- 코드에서 읽기 어려운 **의도, 제약, 호출 계약, 예외 처리 이유**를 설명한다. 메서드명·코드 한 줄을 그대로 번역하는 주석은 작성하지 않는다.
- 소스코드 주석은 **한국어**로 작성한다. C# 식별자·공개 API 이름은 원문을 유지한다.
- 주석은 문장형이 아닌 **요약형**으로, 가능하면 한 줄로 작성한다.
    - 예 : `플레이어의 이동을 처리하는 함수입니다.` (X) → `플레이어 이동 처리` (O)
- 실제로 확인하지 않은 테스트·실행 상태를 주석에 '검증됨'이라고 남기지 않는다.

## 2. XML 문서 주석 적용 대상

- AI가 새로 만들거나 승인된 범위에서 변경한 `public`·`protected` 클래스, 메서드, 프로퍼티, 이벤트, 필드는 간결한 `///` XML 문서 주석으로 역할을 기록한다.
- Unity `Awake`·`Start`·`Update`·`OnEnable`·`OnDisable` 등 생명주기 메서드는 역할이나 호출 순서가 불명확한 경우에만 짧게 설명한다. 모든 생명주기 메서드에 장황한 설명을 반복하지 않는다.
- `private` 구현은 복잡한 판단·계산·버그 회피 이유가 필요한 경우에만 인라인 주석을 단다.

## 3. XML 태그 사용 기준

- `<summary>`: 멤버의 역할과 필요한 동작 계약을 한 줄 요약형으로 작성한다.
- `<param>`: 매개변수 의미·제약이 사용법 이해에 중요한 경우 작성한다.
- `<returns>`: 반환 의미, 성공/실패 조건 또는 null 가능성이 중요한 경우 작성한다.
- `<inheritdoc/>`: 부모나 인터페이스의 문서 설명을 그대로 상속하는 것이 정확한 경우 사용한다.
- API 호출 시 주의할 타이밍, 데이터 소유자, 변경 통지 규칙이 있으면 관련 멤버 설명에 간결히 반영한다.

## 4. 인라인 주석 작성 기준

- 복잡한 분기·계산·동기화·중복 호출 방지·버그 회피에는 `//`로 **왜 필요한지** 설명한다.
- Object Pool 재사용 때 초기화가 필요한 이유, 이벤트 구독·해제의 수명 제약, Coroutine의 중복 실행 방지 등 **실수하기 쉬운 계약**을 선택적으로 설명한다.
- `// 값을 1 증가`처럼 코드 동작을 단순 반복하지 않는다.
- 쓰이지 않는 코드를 주석 처리해 장기간 보관하지 않는다. 변경 이력은 Git에서 확인한다.
- 새로운 자료구조·알고리즘을 도입한 사유가 코드만으로 드러나지 않는 경우 핵심 불변식이나 선택 이유만 남긴다. 장단점·승인 기록 전체를 코드 주석에 복사하지 않고 Issue/기술 문서에 기록한다.

## 5. 코드 주석 적용 예시

```csharp
using UnityEngine;

/// <summary>
/// 플레이어의 현재 체력 상태를 관리
/// </summary>
public class PlayerHealth : MonoBehaviour
{
    [SerializeField] private int _maxHealth = 100;
    private int _currentHealth;

    /// <summary>현재 체력을 반환</summary>
    public int CurrentHealth
    {
        get { return _currentHealth; }
    }

    /// <summary>체력을 감소시키고 0 미만으로 내려가지 않게 처리</summary>
    /// <param name="damage">피해량</param>
    public void TakeDamage(int damage)
    {
        if (damage <= 0)
        {
            return;
        }

        _currentHealth = Mathf.Max(0, _currentHealth - damage);
    }
}
```

> 위 예시는 **주석 표현 형식만** 보여준다. 실제 초기화 흐름과 필드·메서드 구현은 해당 프로젝트 코드에 맞춰 검토해야 한다.

## 6. 주석 수정 시 Agent 점검

- [ ] 설명이 현재 실제 코드와 일치하는가?
- [ ] 공개 API 계약은 표현했지만 불필요한 주석을 늘리지 않았는가?
- [ ] 주석에 확인하지 않은 성능·테스트 결과를 단정하지 않았는가?
- [ ] 승인 범위 밖의 기존 코드·주석은 그대로 보존했는가?

## 7. TODO 주석 관리

- 승인 없이 TODO 주석을 남기지 않는다.
- 형식은 `// TODO : 할 일 (#이슈번호)`로 작성한다. 관련 Issue가 없으면 번호를 생략한다.
- FIXME 등 다른 태그는 쓰지 않고 TODO로 통일한다.
