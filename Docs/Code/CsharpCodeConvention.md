# C# Code Convention

> C# 코드 작성·검토 매뉴얼을 정리한 컨벤션 문서이다.
> 주석은 `CommentConvention.md`를 따른다.

## 1. 코드 네이밍

| 구분 | 표기 | 예시 |
|---|---|---|
| 클래스·구조체·enum | PascalCase | `PlayerController`, `WeaponType` |
| 인터페이스 | `I` + PascalCase | `IDamageable` |
| 추상 기본 클래스(필요 시) | PascalCase + `Base` | `EnemyBase` |
| 메서드 | PascalCase | `TakeDamage()` |
| 프로퍼티·이벤트 | PascalCase | `CurrentHealth`, `OnHealthChanged` |
| 지역 변수·매개변수 | camelCase | `damageAmount`, `targetEnemy` |
| private·protected 인스턴스 필드 | `_camelCase` | `_currentHealth` |
| const | UPPER_SNAKE_CASE | `MAX_WEAPON_LEVEL` |
| 파일명 | 해당 타입명과 일치 | `PlayerController.cs` |

- 변수명에 모든 의미를 충분히 담는다. 약어를 사용하지 않는다.
- 한 가지 예외가 있다면 루프에서 반복을 의미하는 변수는 한 글자 이름이 허용된다.
- 현재 프로젝트에 합의된 도메인 용어(`Enemy`, `Projectile`, `Weapon` 등)를 우선 사용한다.


## 2. 자료형 선언

- 타입 가독성을 위해 **명시적 자료형을 우선** 사용한다.
- `var`는 우변에서 타입이 즉시 분명한 경우만 예외적으로 허용한다.

## 3. 접근 제한자·Inspector·프로퍼티

- 필드는 기본적으로 `private`으로 선언한다.
- Inspector에서 지정·확인이 필요한 필드와 다른 컴포넌트·에셋 참조는 `[SerializeField] private`로 선언하고 Inspector에서 연결한다. Inspector 목적만으로 `public` 필드를 만들지 않는다.
- `Find` 계열 검색은 사용하지 않는다. (호출 비용이 큼)
- 같은 오브젝트의 컴포넌트를 `GetComponent`로 얻어야 하면 `Awake`에서 한 번만 가져와 필드에 저장한다.
- 외부에서 **읽기만** 필요한 값은 읽기 전용 public 프로퍼티를 제공한다.
- 외부에서 변경해야 하면 public setter를 우선 사용한다.
- `protected`는 상속 구조에서 실제 필요한 경우에만 선언한다.
- 값 변경을 다른 객체에 알려야 한다면 `event` 또는 적절한 델리게이트 통지를 검토한다. **값 조회에 이벤트가 필수인 것은 아니다.**

### 3.1 하드코딩 금지

- 숫자·문자열·좌표는 메서드 본문에 직접 쓰지 않는다.
- 해당 값은 클래스 상단에 변수로 선언하고, 그 변수에 값을 대입해 사용한다.

- 값 대입 방식은 아래 기준으로 선택한다.

| 값의 성격 | 선언 방식 |
|---|---|
| Inspector에서 자주 검토·조정해야 하는 값 | `[SerializeField] private` |
| 가변적이지 않은 값 (숫자, `bool`, `string`, `enum`) | `const` |
| 가변적이지 않은 값 중 `const`로 선언할 수 없는 타입 (`Vector2Int`, `Color`, 배열 등) | `static readonly` |

- `static readonly`는 `private`으로만 선언한다. (배열·참조 타입은 참조만 고정되고 내용은 변경될 수 있어, 외부 노출 시 값의 추적이 어려워짐)

#### 하드코딩 예외

아래 값은 메서드 본문에 직접 쓸 수 있다.

| 예외 | 예시 |
|---|---|
| 비교·증감에 쓰는 `0`, `1`, `-1` | `if (damage <= 0)`, `count + 1`, `index == -1` |
| 루프 경계 | `i = 0; i < arr.Length; i++` |
| 0이 아닌 루프 초기값 | `i = 2; i < arr.Length; i++` — 시작 값을 쓴 이유를 주석으로 설명한다 |

```csharp
// 앞의 두 칸은 고정 블록이라 검사에서 제외
for (int i = 2; i < cells.Length; i++)
```

### 3.2 클래스 멤버 배치 순서

- 필드·프로퍼티는 아래 순서로 선언한다.
  1. `const`
  2. `static readonly`
  3. `[SerializeField] private`
  4. `private`
  5. 프로퍼티
  6. `public`
- 초기화(Init) 메서드와 컴포넌트 캐싱(`GetComponent`) 메서드는 클래스의 맨 아래에 둔다.

## 4. `Update()`와 Unity 생명주기

- `Update()` 안에는 **매 프레임 반드시 필요한 처리**만 유지한다. 예: 입력 기반 이동·조준, 지속 갱신이 필요한 시뮬레이션.
- 매 프레임 불필요한 전체 컬렉션 순회, LINQ/문자열 결합 등 할당을 만들 수 있는 처리는 점검하고 필요 시 캐싱·이벤트로 개선을 제안한다.
- `Update()`에 조건문이 있다는 이유만으로 무조건 제거하지 않는다. 요구되는 갱신 빈도와 실제 비용을 비교한다.
- UI 상태와 데이터 갱신은 변경 이벤트에 반응할 수 있는지 먼저 검토한다. 지속적인 폴링이 필요한 경우 이유를 명시한다.

### 초기화 순서와 참조 연결 기준

| 생명주기 | 수행할 작업 |
|---|---|
| `Awake` | 자기 자신의 필드 초기화, 같은 오브젝트의 컴포넌트 캐싱 |
| `OnEnable` / `OnDisable` | 이벤트 구독·해제, `InputAction`의 `Enable()`·`Disable()` (짝을 맞춘다) |
| `Start` | 다른 컴포넌트의 상태나 메서드를 사용하는 초기화 |

- 다른 컴포넌트가 `Awake`에서 초기화를 마쳤다고 가정하는 처리는 `Start` 이후에 둔다.

## 5. Coroutine / 이벤트 / 델리게이트

| 상황 | 우선 검토할 구현 방식 | 판단 기준 |
|---|---|---|
| 상태 변경 시 1회 통지 | `event` / 델리게이트 | 변경 시점이 명확하고 구독자가 반응하면 되는가? |
| 지연 실행·일정 간격 반복·연출 순서 | Coroutine | 시작·중지·오브젝트 비활성화 시 처리가 명확한가? |
| 실제로 매 프레임 갱신해야 하는 동작 | `Update`/`FixedUpdate` 등 | 렌더 프레임인지 물리 스텝인지에 따라 선택 |
| 빈번한 생성·회수 | Object Pool | 인스턴스화·파괴 비용과 풀 유지비용을 비교 |

- **Coroutine은 무조건 `Update()`보다 가볍지 않다.** 매 프레임 `yield return null`인 반복으로 단순 치환하는 것은 피한다.
- 여러 Coroutine이 동시에 시작되는 경우 중복 실행 방지 및 종료 조건을 검토한다.

## 6. Object Pool 구현 검토

- `Instantiate`/`Destroy`가 자주 반복되는 오브젝트(적·탄환·효과 등)에 Object Pool을 검토한다. 생성 빈도가 낮으면 도입하지 않는다.
- 기존 풀이 있다면 중복 구현 대신 재사용한다.
- 풀에서 꺼낼 때 위치·상태·이벤트 구독을 초기화하는지, 중복 반환을 막는지 확인한다.

## 7. 자료구조 선택 기준

| 자료구조 | 적합한 상황의 예 | 도입 전에 확인할 사항 |
|---|---|---|
| `List<T>` | 순차 순회·인덱스 접근·적은 수의 객체 관리 | 중간 삽입/삭제가 매우 빈번한가? |
| `Dictionary<TKey, TValue>` | ID·태그 등 키로 반복 조회 | 고유 키 보장, 중복 키/누락 처리, 순서 의존 여부 |
| `HashSet<T>` | 중복 방지, 포함 여부 확인 | 인덱스·순서가 필요한가? |
| `Stack<T>` | 후입선출(LIFO), 풀의 보관 컨테이너 | 특정 순서가 필요한가? |
| `Queue<T>` | 선입선출(FIFO), 대기열·순서 처리 | 우선순위나 임의 인덱스 접근이 필요한가? |

- 데이터가 적고 순회만 하면 배열이나 `List<T>`를 쓴다. 다른 컬렉션은 위 표의 상황이 실제로 있을 때만 쓴다.
## 8. 알고리즘·그래프 도입 판단

- 작은 컬렉션은 단순 순회나 기본 정렬 API로 해결되는지 먼저 확인한다.
- BFS/DFS·A* 등은 연결 탐색·경로 탐색 문제가 실제로 있을 때만 검토한다.
- 성능 개선을 주장할 때 실제로 측정하지 않았다면 '예상'으로 표현한다.

## 9. 메서드 오버로딩

- 동일한 기능에 여러 입력 형태가 실제로 필요할 때만 오버로딩을 검토한다.
- 단순히 메서드 수를 늘리거나 미래 사용 가능성만으로 추가하지 않는다.

## 10. Unity C# 검증

- `[SerializeField]` 참조가 실제 Scene/Prefab Inspector에서 연결되어 있는지 확인한다. 실행 환경 접근이 없으면 **미검증**으로 보고한다.
- 컴파일, 관련 기능 정상·예외 흐름, 이벤트 중복 구독, Coroutine 중복 시작, 풀 반환 및 데이터 초기화를 점검한다.

## 12. 메서드 길이 및 분리 기준

- 새로 작성하는 메서드는 **한 가지 일**만 한다. 메서드 이름으로 설명할 수 없는 일이 섞이면 분리한다.
- 메서드 본문이 **40줄 이상**이면 기능 단위로 분리를 검토한다.
  - 빈 줄, 그리고 `{`, `}`, `return;`처럼 단어 하나·문자 하나만 있는 줄은 세지 않는다.
  - 분리 여부는 사용자에게 승인받는다.
- 기존 메서드의 분리는 요청이 있을 때만 한다. (`Docs/Claude/ClaudeCodeRules.md` › `외과적 변경`)

## 13. null 및 예외 처리 기준

- Inspector 연결 필드는 코드에서 null 검사하지 않고, Inspector 연결 여부를 확인한다. (§10)
- null 검사는 실제로 비어 있을 수 있는 값(검색·조회 결과, 선택적으로 연결하는 참조)에만 한다.
- `try-catch`는 파일 입출력 등 외부 요인으로 실패할 수 있는 처리에만 쓴다.

## 14. LINQ 사용 세부 기준

- 매 프레임 실행되는 코드(`Update`, `FixedUpdate` 등)에서는 LINQ를 쓰지 않는다. (할당 발생)
- 그 외에는 `for`/`foreach`보다 읽기 쉬울 때만 쓴다.

## 15. 상속·인터페이스 선택 기준

- 기본은 클래스 하나로 구현한다. 구현이 하나뿐이면 상속·인터페이스를 도입하지 않는다.
- 여러 클래스가 **상태와 구현**을 함께 공유하면 추상 기본 클래스(`Base`)를 쓴다.
- 서로 다른 클래스가 **같은 행동(메서드)만** 공유하면 인터페이스(`I`)를 쓴다. (예 : `IDamageable`)
