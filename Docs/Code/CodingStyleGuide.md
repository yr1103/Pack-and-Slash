# Coding Style Guide

> 코드를 검토·설계·수정할 때 따라야하는 가이드 문서이다.
> 현재 코드와 기획을 검토하고, 적절한 구조를 제안·브리핑·승인받은 뒤 구현하도록 한다. 
> **범위:** 클래스 책임, 공통 기능, 설계 대안, 아키텍처, 기술 문서. C# 문법·최적화 상세 기준은 `CsharpCodeConvention.md`, 주석은 `CommentConvention.md`를 참조한다.

## 1. 문서 적용 원칙 및 우선순위

- 업무 단계·승인 시점은 `Docs/Claude/WorkflowRules.md`, 작업 범위·착수 브리핑은 `Docs/Claude/ClaudeCodeRules.md`를 따른다.
- 프로젝트의 기술적 사실(엔진 버전, 렌더 파이프라인, 입력 체계, 배포 대상)은 실제 코드/설정과 `Docs/TechSpec.md`에서 확인한다.
- 규칙끼리 충돌하면 **이해하기 쉬운 코드**를 우선한다.

## 2. 설계 검토·제안 기준

- 구조(풀링, 이벤트, 자료구조 등) 제안은 **요청받은 기능과 직접 관련된 경우에만** 한다.
- 패턴·자료구조·알고리즘은 이름이 아니라 **문제 특성과 예상 이익**으로 선택한다.
- 제안 시 다음 순서로 간결히 설명한다.
  1. **현재 상황:** 현재 코드/기획에서 관찰한 사실과 불확실한 점
  2. **권장안:** 가장 적절한 방식 1개와 선택 이유 (필요하면 대안 1개와 비용 차이)
  3. **영향:** 새로 만들거나 변경해야 할 파일·API·Prefab·Inspector·데이터

## 3. 프로젝트·폴더·클래스 책임

- Script와 폴더를 사람 이름이 아니라 **기능·역할** 중심으로 구성한다. 기존 프로젝트 구조를 우선 읽는다.
- 데이터, 게임 규칙, 입력, UI/표시 책임을 가능하면 분리하되 **클래스 수를 늘리기 위한 분리**를 하지 않는다.
- 클래스가 길어지면 메서드와 같은 방식(`CsharpCodeConvention.md` §12)으로 기능 단위 분리를 검토하고, 분리 여부를 사용자에게 승인받는다.
- `Manager` 접미사는 여러 객체의 상태·수명·흐름을 실제로 총괄할 때만 사용한다.
- 공동 사용되는 기능은 상태와 소유권을 한 곳에 두고 호출부를 명확히 한다.
- 이벤트·Object Pool·자료구조·알고리즘의 선택 기준은 `CsharpCodeConvention.md` §4~8을 따른다.

### 스크립트 폴더 구조

- 스크립트는 `Assets/Scripts/<기능명>/`에 둔다. (예 : `Assets/Scripts/BlockPuzzle/Board.cs`)
- 폴더명은 영문 PascalCase로 작성한다.
- 여러 기능이 함께 쓰는 스크립트의 위치는 구현 브리핑에서 결정한다.

### 3.1 디자인 패턴 검토: Singleton

- **단일 인스턴스가 실제로 필요**하다고 판단되면 Singleton을 제안할 수 있다.
- 제안 전 Inspector 연결 또는 명시적 의존성 전달로 충분한지 비교한다.
- 전역 접근의 편의와 함께 결합도 증가, 중복 인스턴스·초기화 순서, `DontDestroyOnLoad` 필요 여부를 설명한다.
- 자동으로 Singleton을 추가하지 않는다. 도입 범위·책임·수명 주기를 브리핑하고 승인받는다.

### 3.2 SOLID 원칙

- 설계를 검토할 때 아래 원칙을 기준으로 삼는다. 원칙끼리 부딪히거나 코드가 복잡해지면 §1의 "이해하기 쉬운 코드 우선"을 따른다.

| 원칙 | 이 프로젝트에서의 적용 |
|---|---|
| S. 단일 책임 | 클래스는 변경 이유가 하나만 있도록 책임을 나눈다. 실제 변경 이유·재사용 요구를 근거로 분리를 제안한다. |
| O. 개방·폐쇄 | 기능을 추가할 때 기존 코드를 고치는 범위가 최소가 되도록 설계한다. 실제로 확장 요구가 있을 때만 적용한다. |
| L. 리스코프 치환 | 자식 클래스는 부모 클래스 대신 써도 동작이 깨지지 않아야 한다. |
| I. 인터페이스 분리 | 인터페이스는 사용하는 쪽에 필요한 메서드만 갖도록 작게 나눈다. |
| D. 의존성 역전 | 구체 클래스보다 Inspector 연결·인터페이스에 의존한다. |

- 상속·인터페이스를 고르는 기준은 `CsharpCodeConvention.md` §15를 따른다.

## 4. 공통 기능·아키텍처: 사용자 의사결정 지원

| 검토 항목 | AI가 확인하고 사용자에게 필요시 제안할 내용 |
|---|---|
| 책임·소유권 | 어떤 클래스가 상태와 로직을 소유할지, 기존 소유자와 충돌하지 않는지 |
| 입력·출력 | 호출자·피호출자, 매개변수, 반환값, 호출 조건 |
| 상태·데이터 | ScriptableObject·세이브 데이터·Inspector 필드의 원본과 수정 책임 |
| 이벤트 | 알림 조건, 구독자, 해제 시점, 중복 호출 가능성 |
| 의존성 | 기존 스크립트, Prefab, Scene, 참조 순서에 미치는 영향 |
| 예외·실패 | null 참조, 0개 대상, 중복 호출, 수명 종료, 초기화 순서 |
| 검증 | 정상 사례와 작은 실패 사례, Unity에서 확인해야 할 항목 |

- 공용 API·이벤트 이름, 매개변수, 호출 시점 및 데이터 계약을 변경해야 하면 **변경 전/후·영향받는 호출부**를 먼저 설명하고 승인받는다.

## 5. 기술 문서 (`Docs/TechDocs/<SystemName>.md`)

- 주요 클래스 3개 이상이 연결되거나, 여러 컴포넌트가 API 계약·초기화 흐름을 공유하는 경우 기술 문서 작성을 제안한다.

문서 기본 목차:

```markdown
# [시스템 이름]
## 목적 / 기능 범위
## 주요 클래스와 역할
| 클래스 | 책임 | 의존성 |
|---|---|---|
## API / 이벤트 / 데이터 계약
## 호출 순서 또는 데이터 흐름
## Scene·Prefab·Inspector 사용 방법
## 예외·주의사항·검증 방법
## 관련 Issue/PR
```

## 6. AI의 검증·보고 체크리스트

- [ ] 기존 코드·기획·기술 명세를 확인하고 사실/추정을 구분했는가?
- [ ] 기존 방식이 충분한데 패턴·계층을 과도하게 도입하지 않았는가?
- [ ] 공유 API/이벤트/데이터 계약 변경을 승인받았는가?
- [ ] 변경 대상 파일·Scene·Prefab·Inspector 연결을 명시했는가?
- [ ] 정상·실패 사례의 확인 결과와 미검증 항목을 구분하고, 실제 완료하지 않은 검증을 완료로 표시하지 않았는가?
